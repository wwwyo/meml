1.What — この PR は何をするか

ローカル markdown を meml add <path> で DuckDB に取り込み、agent が meml sql から raw SQL で構造化 + semantic 両方を query できるようにする Phase 0 実装。あわせて、後続 source plugin (RSS / PDF / 画像) が乗る基盤 (DuckDB + vss / embedding pipeline / CLI 骨格) を確立する。

この PR 特有の言葉だけ先に定義する（一般用語は省略）:

source_id
UNIQUE(source, source_id) の identity 列。md は realpath、RSS は GUID、GitHub PR は owner/repo/pull/N のように source ごと canonical な ID を入れる。URL を持たない source でも壊れない identity。
meml_embed('text')
meml sql 内でのみ使える pseudo-function。CLI 側 preprocessor が literal を 1 回だけ embed し $qvec_N param に bind してから DuckDB に渡す (DuckDB の scalar UDF ではない)。行ごと HTTP 評価リスクと read-only 衝突を回避する設計。
READ_ONLY connection
DuckDB access_mode: "READ_ONLY" で開いた接続。engine が DB ファイルへの書き込みを拒否する。ただし read_csv/COPY TO 等の filesystem 系副作用は別途遮断が必要。
enable_external_access = false
DuckDB の engine 設定。read_csv / read_text / glob / COPY / ATTACH / network を一律遮断する。本 PR では read-only connection で LOAD vss 後に有効化し、agent SQL からの任意ファイル read/write を engine レベルで止める。

設計ドキュメント (gitignore された .agent/prd/local-markdown-ingest/ に prd/dd/decision.log) はリポジトリには含まれないため、リンク先は AGENTS.md (アーキテクチャ / 設計思想) を参照する。

6.Data Model Changes High · 戻せない

DB に保存される構造と、meml schema 経由で agent に見える契約。今回 schema を確定するため、後で変えると user の既存 DB の migration が要る。

DB schema (memory + memory_chunks) を確定する。

CREATE TABLE IF NOT EXISTS memory (
  id          TEXT PRIMARY KEY,        -- UUID v7 (内部 surrogate)
  source      TEXT NOT NULL,           -- "md" | "rss" | ...
  source_id   TEXT NOT NULL,           -- source 内 canonical (md=realpath)
  url         TEXT,
  title       TEXT NOT NULL,
  content     TEXT NOT NULL,
  author      TEXT,
  tags        TEXT[],
  sourced_at  TIMESTAMPTZ,             -- source 側 mtime 等
  metadata    JSON,                    -- source 固有 raw
  created_at  TIMESTAMPTZ NOT NULL,    -- 初回 ingest
  updated_at  TIMESTAMPTZ NOT NULL,    -- 最終 ingest (UPSERT で更新)
  UNIQUE (source, source_id)
);

CREATE TABLE IF NOT EXISTS memory_chunks (
  id              TEXT PRIMARY KEY,
  memory_id       TEXT NOT NULL,       -- logical 参照、FK ではない
  chunk_index     INTEGER NOT NULL,
  content         TEXT NOT NULL,
  embedding       FLOAT[1024],         -- bge-m3 固定次元
  embedding_model TEXT NOT NULL,       -- 混在検知用
  UNIQUE (memory_id, chunk_index)
);
  • TIMESTAMPTZ (UTC instant) を採用。当初 dd 通り naive TIMESTAMP だったが、DuckDB の now() は TIMESTAMPTZ なので session TZ 分の skew が出ていた。PRD の success metric query 自体が WHERE sourced_at > now() - INTERVAL 30 DAY と書くので実害。make_timestamp($us) AT TIME ZONE 'UTC' で UTC instant を bind する
  • FK 撤廃。dd は REFERENCES memory(id) ON DELETE CASCADE だったが、DuckDB FK は (a) CASCADE 宣言不可、(b) delete→再 insert / 親削除で参照エラー、で UPSERT と remove が両方壊れた。memory_id は logical (app-enforced) 参照に降格し、cascade は transaction 内で明示的に再現
  • embedding FLOAT[1024] 固定。bge-m3 (llama-server) に依存。別 model に切り替える場合は別 column or 別 table が必要。embedding_model 文字列を 1 chunk ごとに記録して混在検知できる
  • UNIQUE(source, source_id) を全 source の identity に。md は realpath、後続予定: RSS=GUID、GitHub=owner/repo/pull/N、Slack=channel+ts。UNIQUE(source, url) 案だと url を持たない source で NULL 抜けする問題を回避
  • schema は migration runner で管理: schema_migrations(version, applied_at) で適用済みを記録し、番号付き .sql をファイル順に各 1 transaction で適用 (冪等)。baseline 0001_init.sql は immutable なので FLOAT[1024] 等は literal で焼く。Phase 1 の column 追加は 0002_*.sql を足すだけ
なぜ「戻せない」のか（前提から）
dd の方針として agent は raw SQL を唯一の interface として使う。これは ORM/wrapper を挟まないので柔軟だが、代わりに DB schema が agent から見える契約になる。column 名や型が後で変わると、agent が meml schema を読んで組み立てた既存の query 文字列 (or agent 自身の学習) が壊れる。さらに DuckDB の column 型変更は ALTER TABLE ... ALTER COLUMN ... TYPE ... で書けるが既存データの cast が要り、特に NOT NULL を後付けすると既存 row の backfill が必要。今回確定する axis のうち FLOAT[1024] 次元は model 依存、TIMESTAMPTZ は agent クエリの now() 比較に直結、UNIQUE(source, source_id) は全 source 共通 identity の前提として後続 plugin に乗る — 後から差し替えると後続 plugin と既存データの両方を巻き込む。

検知方法: ~/.agents/skills/review-guide/scripts/pr-diff.sh -- 'src/storage/migrations/0001_init.sql' 'src/storage/migrate.ts' 'src/commands/schema.ts' で literal を直視。baseline の FLOAT[1024] は immutable な migration に焼かれ、runtime 側 (repo.ts / schema.ts) は src/config.ts の EMBED_DIM を使う。meml schema 出力には FUNCTIONS (vss + meml_embed) も含まれるので、agent が array_cosine_similarity 等を引ける契約も同時に決まる (schema_migrations は契約に露出しない)。

7.Permission Changes High · security

meml sql は agent に raw SQL を投げさせる唯一の境界。memo 内容が prompt injection を含む可能性があるので、agent SQL は untrusted として扱う必要がある。

3 段 enforcement の正しさが核心。

// src/storage/db.ts
const options = mode === "read-only" ? { access_mode: "READ_ONLY" } : undefined;
const instance = await DuckDBInstance.create(path, options);
const conn = await instance.connect();
await loadVss(conn, mode === "read-write");   // read-only は LOAD のみ (INSTALL なし)
if (mode === "read-only") {
  await conn.run("SET enable_external_access = false");  // LOAD vss の後
}

// src/sql/guard.ts (allowlist)
const FORBIDDEN = [
  "INSERT","UPDATE","DELETE","CREATE","DROP","ALTER","ATTACH","DETACH",
  "COPY","INSTALL","LOAD","PRAGMA","CALL","SET","RESET","EXPORT","IMPORT",
  "VACUUM","CHECKPOINT","TRUNCATE","MERGE","GRANT","REVOKE","ANALYZE","USE",
];
// 先頭が SELECT or WITH のみ許可、string literal / comment / dollar-quote を中和してから keyword 走査
  • 層 1 (engine): READ_ONLY connection — DB ファイルへの書き込みを engine が拒否。bypass 不可
  • 層 2 (engine): SET enable_external_access = false — read_csv / read_text / glob / COPY TO / ATTACH / network を engine 設定で遮断。query() でネストしても内側の file access ごと遮断される。これが本丸の防御 — keyword allowlist では DuckDB の table function 群を列挙しきれないので、engine 側で禁止する
  • 層 3 (parser): statement allowlist — 単一 statement / 先頭 SELECT or WITH / 書き込み・副作用 keyword 拒否。明快なエラーを返す defense-in-depth。dollar-quote ($$..$$ / $tag$..$tag$) を中和してから keyword 走査することで literal 内 DROP の誤検知と multi-statement 隠蔽の両方を回避
  • meml_embed の bind 名衝突回避 — preprocessor は呼び出しごとに q<8hex> ランダム prefix を生成し $q<hex>_N を emit する。user が偶然 $qvec_1 を書いても自身の embedding vector を踏まない
  • ingest path (read-write conn) には enable_external_access=false を掛けない。add / remove は user SQL を実行せず内部 parameterized SQL のみで攻撃面が無いため
なぜ危険か（前提から）
meml の使い方は「agent が memo を文脈に raw SQL を生成して投げる」。prompt injection = ingest した memo の本文が agent への指示として読まれるリスク。injection された SQL が untrusted 入力として meml sql に渡る前提で防御を組む必要がある。DuckDB は table function (read_csv, read_text, glob, query) で任意ファイル read / COPY TO で任意ファイル write ができるので、これらが通ると arbitrary local file exfiltration / overwrite になる。READ_ONLY mode だけでは DB 書き込みしか止まらず file IO は通る点を見落とすと穴になる。keyword denylist で塞ぐ案は DuckDB が任意 SQL を実行する query('...') table function を持つため原理的に列挙しきれない。engine 設定 (enable_external_access) でカテゴリごと禁止するのが正解。

検知方法: ~/.agents/skills/review-guide/scripts/pr-diff.sh -- 'src/storage/db.ts' 'src/sql/guard.ts' 'src/sql/preprocess.ts' 'src/sql/scan.ts' で 3 段それぞれの diff を直視。test/security.test.ts が read_text('/etc/hosts') / query('...read_text(...)') / COPY (SELECT 1) TO '...' の 3 種の遮断を回帰確認する。dollar-quote 中和の回帰は test/guard.test.ts と test/preprocess.test.ts に追加されている。
